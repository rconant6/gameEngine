0. Executive summary

The renderer's architecture is right: an immediate-mode draw API feeding a CPU-side batch that flushes once per frame into pre-allocated GPU buffers. The problem is that the implementation defeats the batch at the last step — nearly every triangle and line becomes its own GPU draw call — and the Metal frame lifecycle has correctness gaps (no CPU/GPU synchronization, per-frame object leaks, no blending on shapes) that will bite harder as scenes grow.

The plan is six phases. Phase 0 makes frames safe (sync, leaks, buffers, blending, resize). Phase 1 is a one-sitting change that merges adjacent draw calls and adds stats counters — it should take a PONG frame from ~80 draw calls to under 5. Phase 2 centralizes tessellation into a backend-agnostic module, which makes stroke_width real, removes the World/Screen code duplication, and is the platform every new shape lands on. Phase 3 is the visible payoff: rounded rects, capsules, arcs/rings, n-gons, MSAA, working opacity, gradients. Phase 4 makes RenderLayer.z_order real and fixes the "sprites always render on top of shapes" ordering flaw. Phase 5 is on-demand scaling work (atlases, culling).

status 2026-07-15 Phases 0 (−resize), 1, 2, 3 are DONE, plus a GPU-transform staircase that reversed D2 (linear color + camera→clip + LocalXform all on the GPU). Phase 4 is the frontier and grew in scope: it is now 4a (single unified indexed pipeline + z-order — reverses D3, pulls indexed drawing forward from P5, and rewrites tess.zig ~500→~80 lines) and 4b (SDF text atlas + producer-seam collapse — supersedes P5's glyph-atlas item). The original Phase 4 sketch below is kept for the decision trail; 4a/4b are authoritative.

Decisions are made throughout and collected in the decision log — each one notes what was rejected and why, so any of them can be re-litigated before implementation.

1. How a frame works today

engine.beginFrame() engine.zig:339 └─ app.beginFrame() app.zig:108 ├─ poll platform events └─ renderer.beginFrame() MetalRenderer.zig:257 ├─ batch.clear(), texture_batch.clear() ├─ nextDrawable() ← BLOCKS on vsync, held for the whole frame └─ create MTLCommandBuffer game logic (user code) examples/pong/main.zig:66-114 engine.update(dt) ├─ simulate(dt) action/physics/movement/collision/camera └─ render(dt) RenderSys.run RenderSys.zig:22 ├─ query(Transform, Sprite) → drawGeometry → GeometryBatch.addShape ├─ query(Transform, Text) → drawText → one addTriangle per glyph triangle ├─ query(UIElement, Sprite) → drawGeometry (screen-space ctx) ├─ query(Transform, ZxlSprite)→ drawTextureQuad → TextureBatch.addSprite └─ debugger.run(dt, ctx) → same paths engine.endFrame() MetalRenderer.zig:267 ├─ create render pass descriptor + encoder ├─ memcpy geometry vertices → single shared MTLBuffer (no sync with GPU) ├─ one drawPrimitives() per DrawCall (≈ per triangle/line) ├─ memcpy texture vertices → 256KB buffer (no bounds check) ├─ one setFragmentTexture + drawPrimitives per sprite └─ present + commit

Key structural facts:

  • All vertex math happens on the CPU. Shaders are pass-throughs (shaders.metal): position and color/uv go in clip-space, come out unchanged. Camera, local transform, and tessellation are all CPU work, per vertex, per frame.
  • Vertex = 24 bytes ([2]f32 pos + [4]f32 color). TextureVertex = 16 bytes (pos + uv). Two pipelines: geometry (no blending) and texture (alpha blending).
  • Two strictly ordered flush passes: all geometry, then all textures. Painter's order only holds within each pass.
  • ShapeData is a comptime-generated union of every shape in shapes.zig × {WorldPoint, ScreenPoint} (shape_registry.zig:12). The scene instantiator maps scene fields to shape struct fields by comptime reflection — new shapes are nearly free on the data side.

2. What's already good (keep these)

Worth protecting through the refactor
  • Comptime shape registry — ShapeData auto-derives from shapes.zig decls; scene field mapping is reflection-driven. Adding a shape struct is ~zero plumbing. This is the extension mechanism the whole plan builds on.
  • Batch-then-flush architecture — the right shape for a 2D engine. The fix is in the flush, not the design.
  • Polygon triangulation cache (shapes.zig:159) and glyph triangle cache (text.zig:107) — tessellate-once, reuse-forever is exactly right; Phase 2 extends this idea to circles.
  • Backend isolation — Renderer switches implementation at comptime via build_options.backend; the FFI bridge is one file per side. The plan keeps this boundary and shrinks the FFI surface.
  • Frame-texture lazy cache (TextureManager.getFrameTexture) — uploads once, caches per frame, hot-reload aware.

3. Findings: stability & correctness

These are bugs, not style issues. They're listed first because every later phase assumes a stable frame.

S1 · No CPU↔GPU synchronization on vertex buffers
MetalRenderer.zig:295-326, 341-352

One shared MTLBuffer (storageModeShared) is memcpy'd in endFrame every frame. Nothing waits for the previous frame's command buffer to finish reading it. When the GPU runs behind (heavy frame, window drag, vsync backpressure), the CPU overwrites vertices mid-read → flicker/garbage geometry. Same for the texture vertex buffer. Classic fix: a ring of 3 buffers + a completion-handler semaphore.

S2 · Swift bridge leaks ~5 Objective-C objects per frame
MetalBridge.swift:24-31 (cmd buffer), 58-62 (drawable), 63-67 (drawable texture), 158-163 (pass descriptor), 197-209 (encoder)

Every per-frame bridge call returns Unmanaged.passRetained(...) and nothing ever releases. At 60fps that's ~300 leaked objects/sec, and retained drawables fight the CAMetalLayer drawable pool (it only has ~3). MetalRenderer.deinit has a TODO acknowledging no releases happen anywhere. There's also no autoreleasepool around the frame on the Zig-driven thread.

S3 · Geometry vertex buffer is 288 MB (intended: 12 MB)
MetalRenderer.zig:39, 85-88, 239-243

MAX_VERT_SIZE = 1024*1024*12 is commented "12MB of vertices storage" but is then multiplied by @sizeOf(Vertex) (24) → a 288 MB unified-memory allocation. Meanwhile drawShape uses the same constant as a vertex count in its "flush early" check — which doesn't flush, just logs a misleading warning ("Failed to flush batch"). Three different semantics for one constant.

S4 · Texture flush has no overflow guard
MetalRenderer.zig:341-352

flushTextureBatch memcpys vertices.len * 16 bytes into a fixed 256 KB buffer with no size check. More than 2,730 sprites in a frame silently corrupts whatever Metal allocated after the buffer. The geometry flush at least clamps; this one doesn't.

S5 · Geometry pipeline has alpha blending disabled
MetalBridge.swift:120-155 (vs. texture pipeline: 330-334)

metal_create_render_pipeline_state never sets isBlendingEnabled. Vertex colors carry alpha but it's written straight to the framebuffer — every shape, every glyph, every debug overlay renders fully opaque. Anyone setting #RRGGBBAA in a scene file or fading text gets silently ignored. The texture pipeline does blend, so sprites behave differently from shapes.

S6 · Window resize is a no-op
MetalRenderer.zig:162-167; GameWindow.swift:107-111

resize() updates width/height fields and stops. drawableSize is set exactly once, when the layer is first fetched. Resizing the window stretches/blurs output and desyncs the aspect math in worldToClipSpace against the actual drawable.

S7 · Sprites always render on top of all shapes
MetalRenderer.zig:280-281; Components.zig:53-55

Geometry flushes before textures, unconditionally. A UI panel (shape) can never draw over a ZxlSprite; HUD-over-character is impossible. Related: RenderLayer { z_order } exists as a component but no system reads it — render order is ECS storage order. Fixed properly in Phase 4.

S8 · Frame timing quantized to whole milliseconds, owned by each game
examples/pong/main.zig:59-64

Examples compute dt from a millisecond clock: at 60Hz dt alternates 16/17ms (±3%), which reads as micro-stutter in linear motion. Every game re-implements this. The engine should own timing at nanosecond precision and hand dt out.

Every one of those calls also crosses Zig→Swift FFI (metal_render_encoder_draw_primitives → Unmanaged.fromOpaque → objc dispatch). Since consecutive calls share pipeline and buffer, calls with the same primitive type and contiguous vertex ranges can be merged mechanically — order preserved, zero visual change. addPolygon's fill already does this correctly for its own triangles, which proves the pattern.

P2 · All transform math on CPU, per vertex, with per-vertex sin/cos
geometry_utils.zig:18-27 (rotatePt), geometry_batch.zig:423-513 (addCircle)

rotatePt evaluates cos/sin for every vertex instead of once per shape. addCircle re-tessellates 32 segments every frame with 2 transcendental calls per segment — and computes each perimeter point twice (segment i's p2 = segment i+1's p1). A rotating circle pays ~256 sin/cos per frame. The vertex shader does nothing that could absorb this. Fixes: per-shape 2×3 matrix (cos/sin once), unit-circle LUTs, and moving the camera→clip transform to the GPU as a per-pass uniform.

P3 · One draw call + texture bind per sprite, no atlas
texture_batch.zig:35-76; MetalRenderer.zig:357-365

TextureBatch.addSprite appends a draw call per quad; flush sets the fragment texture per call even when consecutive sprites share one. Each Zxl animation frame is also its own MTLTexture, so animation guarantees texture switches. Run-merging is trivial now; an atlas is the Phase 5 fix.

P4 · Text goes through full shape dispatch per glyph triangle
text.zig:115-133, 155-173

Glyph triangles are cached (good), but each one is wrapped in a ShapeData union, dispatched through addShapeDispatch, transform-branched per vertex, and given its own draw call. A 100-char HUD ≈ 3–5k vertices of avoidable per-frame overhead plus thousands of calls. P1's merging absorbs the draw calls; Phase 2's tessellator gives text a direct "append pre-transformed triangles" path.

P5 · 24-byte vertex; color as 4×f32
metal_types.zig:40-43

Flat-shaded 2D needs 4 bytes of color, not 16. unorm4x8 halves vertex size to 12 bytes — halves the per-frame memcpy and GPU fetch. Free win bundled into the Phase 2 shader rev.

P6 · No visibility culling
RenderSys.zig:58-78

Off-screen entities are fully tessellated, transformed, and submitted. The camera's ortho bounds are already computable (getCameraViewBounds exists); a conservative AABB test in RenderSys skips the entire cost. Matters once worlds are bigger than one screen — Phase 5.

P7 · Drawable acquired at frame start and held throughout
MetalRenderer.zig:261

nextDrawable() can block ~a full vsync when the pool is starved; calling it in beginFrame serializes that wait before simulation instead of overlapping. Apple's guidance: acquire as late as possible — here, in endFrame after batching. Combined with S2's retained drawables, today's pattern is maximally pool-hostile.

5. Findings: API & mechanics

A1 · stroke_width is accepted everywhere and honored nowhere
geometry_batch.zig: every addX starts with _ = stroke_width

Scene files, the Inspector, and Sprite all carry stroke_width; the Metal path draws 1px hairlines regardless (line primitives can't be widened on Metal, and wide lines are optional on Vulkan). Phase 2 tessellates strokes as triangles, making the parameter real and uniform across backends.

A2 · Positional-optionals draw signature

drawGeometry(shape, transform, fill_color, stroke_color, stroke_width, ctx) reads as a mystery at call sites and grows a parameter per new style feature. Plan: a DrawStyle struct with defaults (fill, stroke, width, opacity, later gradient), one new drawShape(shape, transform, style, ctx) entry point, old signature kept as a thin wrapper until callers migrate.

A3 · World/Screen duplication doubles the batch code
geometry_batch.zig — ~60% of its 533 lines is if (PointType == ScreenPoint) branching

Every shape × every vertex picks between makeVertex/makeScreenVertex. Both spaces are just different affine maps to clip space. Phase 2 collapses this to a single tessellation path parameterized by one ClipMap (scale+offset), chosen per draw. New shapes then get written once, not twice.

A4 · Silent no-op and dead API surface
geometry_batch.zig:515-531; shapes.zig:211-218; EngineRender.zig:7-11; RenderContext fields
  • Ellipse is registered in the union and parseable from scenes, but addEllipse is an empty body — scene authors get nothing, no error.
  • EngineRender.draw() calls renderer.drawShape(shape_union, xform) — an arity that doesn't exist; it only compiles because Zig lazily analyzes unused decls. Dead API.
  • RenderContext.time / frame_number / scale_factor are hardwired to 0/0/1.0 by RenderSys every frame; MetalRenderer.start_time/last_frame_time/scale_factor are likewise dead. Either feed them honestly (engine has all three) or drop them. Phase 2 feeds them — shader effects and px-accurate strokes will want time and scale.
A5 · Scene format has no integer type

Supported value types are vec2/vec3/f32/string/color/bool. Z-order (RenderLayer.z_order: i32), n-gon side counts, and similar fields can't be expressed. Small lexer/parser addition, needed by Phases 3–4.

Phase 0 — Stable frame foundation DONE: S1–S5, S8 S6 (resize) deferred to Vulkan bring-up

Goal: every later phase assumes frames that don't race, leak, or lie. Nothing here changes what's drawn.

0.1 Frame lifecycle bridge — full specification (fixes S1, S2, P7)

This is the detailed spec for the rewrite. It replaces the per-frame object soup with a two-object model and a strict ownership contract. The S2 memory leak (the ~1 MB / 10 s the renderer is bleeding) is fixed here directly.

Root cause of the leak (S2), object by object

Five bridge functions on the hot path each do Unmanaged.passRetained(x).toOpaque() — i.e. they hand Zig a +1 retain count — and nothing on either side ever calls release. MetalRenderer.deinit literally has // TODO: Release all the MTL resources. Per frame, leaked:

metal_create_render_pass_descriptor:158-163MTLRenderPassDescriptornever
metal_command_buffer_create_render_encoder:197-209MTLRenderCommandEncodernever

Five objects × ~300–400 B effective ≈ ~1.7 KB/frame → ~1 MB per 10 s @ 60 fps, matching the observed growth. (The drawable's multi-MB IOSurface is not in this total — present recycles it — which is why the bleed is KB/frame, not MB/frame.) There's also no autoreleasepool wrapping the frame on the Zig-driven thread, so even autoreleased temporaries created inside these calls have no drain point.

The rule the new design enforces: any object handed across FFI as a pointer is owned by exactly one side, and the function name says which. *_begin/create_* transfer ownership to Zig (Zig must pass it back to a *_end/*_release); everything else is borrowed for the duration of the call only.

The pass descriptor is created, consumed by makeRenderCommandEncoder, and dropped inside metal_frame_begin — it never crosses FFI, so it can't be leaked. Same for the drawable's texture: used to set the color attachment internally, never returned.

Zig side — MetalRenderer changes (as built)

As-built note

Two things landed differently from the first sketch and are now the source of truth: (1) frame_index is u8 indexed @mod(idx, 3), not u2 — u2 wraps 0→1→2→3→0 and would index a nonexistent 4th buffer. (2) Memcpy and draw stay in one function per pass (combined, "option B"); there is no separate uploadBatches. The flush functions take (encoder, idx) and do slot copy + draw together — fewer moving parts, and upload-on-another-thread isn't needed at this scale.

pub fn beginFrame(self: *Self) !void {
    self.batch.clear();
    self.texture_batch.clear();
    self.frame_index +%= 1;              // advance ring; 0,1,2,0,... (mod at use)
    self.frame_number += 1;
    // NO Metal calls here anymore — drawable acquired late (fixes P7)
}

pub fn endFrame(self: *Self) !void {
    const frame = MetalBridge.frameBegin(self.frame_ctx, ClearColor.fromColor(self.clear_color))
        orelse return;                   // NULL => drop frame, buffers untouched, NO clear
    const idx = @mod(self.frame_index, 3);
    const enc = MetalBridge.frameEncoder(frame);
    try self.flushGeometryBatch(enc, idx);         // memcpy slot[idx] + draw
    try self.flushTextureBatch(enc, idx);          // memcpy slot[idx] + draw + S4 guard
    MetalBridge.frameEnd(self.frame_ctx, frame);   // releases frame, signals on GPU done
}

// flush = one function per pass, (encoder, idx). Copy is clamped to a vertex
// multiple of SLOT_BYTES / TEX_SLOT_BYTES (S4 now covers BOTH passes; the
// texture pass had no guard before). setVertexBuffer binds buffers[idx].

    self.batch.deinit();
    self.texture_batch.deinit();
    for (self.vertex_buffers) |b| MetalBridge.release(b);
    for (self.texture_vertex_buffers) |b| MetalBridge.release(b);
    MetalBridge.release(self.pipeline_state);
    MetalBridge.release(self.texture_pipeline_state);
    MetalBridge.frameContextDestroy(self.frame_ctx);   // closes the deinit TODO
}

Why the wait gates correctness (S1): metal_frame_begin blocks on the semaphore before the flush writes buffers[idx]. With value=3, the CPU can be at most 3 frames ahead, and slot N is only rewritten after the command buffer that last read it ran its completion handler. No fence math on the Zig side; the semaphore is the whole sync mechanism. Init-time objects stay passRetained forever — correct for process-lifetime resources.

Two known gaps deferred to 0.2 (do NOT fix in 0.1)
  • Overflow still draws garbage. When a flush clamps the vertex copy, the draw_calls loop still issues draws whose vertex_start + vertex_count reach past the clamp into stale buffer bytes → junk triangles. Pre-existing behavior (the old geometry path had it too). 0.2's real fix trims the draw list at the clamp boundary; the ring-grow makes clamping rare anyway. 0.1 matches current behavior (log + truncate). If a blank-on-overflow frame is preferred meanwhile, return after the log instead of drawing.
  • deinit doesn't drain in-flight frames. Releasing a ring buffer while its command buffer is still on the GPU is a use-after-free. Harmless on a clean Esc-to-quit (GPU idle), but 0.2 should acquire the semaphore FRAMES_IN_FLIGHT times before the buffer releases to guarantee the GPU is done.

Verifying the fix

Before: leaks <pid> after 60 s shows ~3,600 each of MTLCommandBuffer, render encoder, and descriptor (one per frame). After: those counts stay flat; RSS is stable over a 10-minute soak. This is the explicit Phase 0 soak check in §7.

0.2 Right-size buffers with a sane overflow policy (fixes S3, S4)

  • Geometry ring: 2 MB per slot (≈87k vertices of 24B; ≈175k after Phase 2's 12B vertex). Texture ring: 512 KB per slot. Total GPU memory: 7.5 MB instead of 288 MB.
  • One overflow policy in both flushes: if bytes > capacity → truncate this frame's copy at a vertex boundary, log throttled (once/second), set pending_grow = needed_bytes. Next beginFrame waits out all in-flight frames (3 semaphore acquires), reallocates the ring ×2, releases old buffers. No corruption, no permanent truncation. Also trim the draw_calls list at the clamp boundary — 0.1 leaves this undone (see the deferred-gaps note under 0.1), so overflow currently draws past-the-clamp garbage until this lands.
  • Drain on deinit: before releasing the ring buffers, acquire the semaphore FRAMES_IN_FLIGHT times (blocks until every in-flight frame's completion handler has fired → GPU provably idle), then signal it FRAMES_IN_FLIGHT times to restore its original value. The rebalance is mandatory: libdispatch aborts ("Semaphore object deallocated while in use (current value < original value)") if a DispatchSemaphore is deallocated below the value it was created with. The re-signal doesn't weaken the barrier — nothing is submitting frames during teardown, so the restored permits are never consumed; they exist only so the semaphore can dispose cleanly. Do the wait+signal as the FIRST thing in deinit, before any release.
  • Delete the fake "flush early" check in drawShape and the MAX_VERT_SIZE constant; capacity lives on the ring.

0.3 Enable blending on the geometry pipeline (fixes S5)

Same straight-alpha config the texture pipeline already uses (sourceAlpha / oneMinusSourceAlpha, both channels). Premultiplied alpha was considered and deferred — see D6.

0.4 Implement resize (fixes S6) DEFERRED — parked until Vulkan is live

Deliberately left stubbed as of 2026-06-30. Resize is the one Phase 0 item that is inherently cross-backend — it couples the platform resize callback to the render backend's swapchain/drawable sizing. Wiring it fully on Metal while the Vulkan backend is still a non-running skeleton would bake a Metal-shaped assumption (drawable-size model, single color target) into the platform→renderer contract that would then have to be reworked for Vulkan's swapchain-recreation model. The model

The vertex buffer holds every drawable's vertices; the index buffer says how to connect them; a DrawCall is a slice of the index buffer plus where its vertices begin.

GPU call: drawIndexedPrimitives(index_count, ibuf, index_start*2, base_vertex). For each index i it fetches vertices[base_vertex + i].

fieldmeaningset by
base_vertexwhere this shape's verts beginvertexMark() before tess runs
index_startwhere this shape's indices beginindexMark() before tess runs
index_counthow many indices it wroteindexMark() after − before
sort_keyz-ordercaller — only it knows the layer

The invariant everything rests on: emitV returns base-relative indices (vertexMark() - self.base), so a shape's own indices are always 0..n. That is why topo_table.quad = {0,1,2,0,2,3} can be a compile-time constant — it is true for every rect, anywhere in the buffer. The GPU adds base_vertex back at fetch.

Consequence: indexed draws imply the vertex range. vertex_start/vertex_count are the non-indexed model — they are dead.

  • emitTopology(t, base) — u16, shape-relative: the index returned by the first emitV of that primitive.

shaders.metal — EDIT (SDF branch)

The one spot the "one pipeline" ideal gets slightly muddied: the white texel is RGBA, the SDF atlas is R8. Two clean resolutions — decide at impl:

// (a) one pipeline + is_sdf flag (small per-draw uniform, buffer index 3):
float field = tex.sample(s, uv).r;
float w     = fwidth(field) * 0.75;            // edge softness
alpha = is_sdf ? smoothstep(0.5-w, 0.5+w, field) : sampled.a;
return float4(in.color.rgb, in.color.a * alpha);
// (b) two fragment funcs (shapes+sprites / SDF text), sharing the vertex func +
//     buffers, clustered by band → ~2–3 pipeline switches/frame (still >> the D3 win).

open Lean (a) to preserve one-pipeline; (b) is fine because text clusters into one band. This is the last open impl decision in 4b.

Open impl decisions (surfaced, not blocking)

  • uv on Renderable vs. a quad ShapeData variant — where glyph/sprite corner uvs ride. Lean: uv: ?[4][2]f32 on Renderable (as drawn above).
  • SDF sampling vs. one-pipeline purity — 1 pipeline + is_sdf uniform vs. 2 fragment/pipelines clustered by band. Both beat today.
  • Draw-call merging under indexing — deferred to P5 (// TODO: merge contiguous same-base runs). 4a accepts N indexed draws; the sort keeps rebinds rare.

Phase 5 — Throughput at scale on-demand, profile first

  • Culling (P6): camera AABB vs. conservative shape AABB before tessellation. Polygon/Polyline cache bounds at init; circles/rects derive trivially. UI band never culled. ~Day of work, gated on actually building scenes larger than the screen.
  • Texture atlas (P3's other half): TextureManager shelf-packs all frames of a Zxl asset into one texture at load; frames become UV rects, animation stops breaking batches. Pixel-art frames are small — a 1024² atlas holds hundreds.
  • Indexed drawing — MOVED to 4a pulled forward: index-buffer ring + drawIndexedPrimitives land in 4a (the ordered flush needs the seam anyway). Remaining P5 slice: merging contiguous same-base runs into one indexed draw (4a does one draw per tessellate).
  • Glyph atlas for small text — SUPERSEDED by 4b 4b goes further: SDF atlas, not a coverage atlas, and it becomes the DEFAULT text path (not a small-text special case). The "vector text crisp at any zoom" argument is what SDF preserves — one cached texture, sharp at any scale. Vector-triangle glyphs die.
  • Back-face culling: cullMode=.back, front-face CCW. 4a's comptime winding guard already froze the convention for the fixed topologies + fan/ring. Must exclude poly (ear-clipper winding) and strokes (butt-join winding flips with edge direction) — see 4a's emitTopology note.
  • Vulkan parity: the tessellator + ordered stream are backend-agnostic by construction; the Vulkan backend (currently a 276-line skeleton) implements the same ring-buffer flush against the existing swapchain plan docs. Explicitly out of scope until the Metal path proves the interfaces.
